# premium-cars-backend

REST API of the Premium Cars Import website: catalog, import of cars by link, landed price in Bulgaria, inquiries.
Java 21 · Spring Boot 3.5 · plain SQL through `JdbcClient` (no JPA) · PostgreSQL · Liquibase.

The full guide for running all three parts locally is in the **premium-cars-infra** repo (`README.md`).

## Quick start

```bash
# 1. PostgreSQL + Vault (from premium-cars-infra; it prepares the secrets, see its README)
docker compose up -d

# 2. the backend (reads its secrets from Vault)
mvn spring-boot:run
```

- http://localhost:8080/actuator/health → `{"status":"UP"}`
- http://localhost:8080/api/public/cars → the demo cars
- http://localhost:8080/swagger-ui.html → all API endpoints (`APP_API_DOCS=false` turns them off)

Tests: `mvn test`. `JdbcRepositoriesTest`, `AdminAuthTest` and `VaultConfigTest` start PostgreSQL / Vault in
Docker; without Docker they are skipped (CI fails if the database tests are skipped). Tests need no Vault setup.

## Secrets (Vault)

No password, token or key is in this repo, in `application.yml` or in `.env`. They live in HashiCorp Vault
(KV v2, path `secret/premium-cars/backend`) under the names the placeholders in `application.yml` use:

| Key | What |
|---|---|
| `DB_USERNAME`, `DB_PASSWORD` | PostgreSQL (set by the infra setup from `premium-cars-infra/.env`) |
| `ADMIN_INITIAL_PASSWORD` | first admin password, generated by the infra setup (used once, see Admin login) |
| `AUTOWINI_USER`, `AUTOWINI_PASS` | autowini account |
| `FB_PAGE_ID`, `FB_ACCESS_TOKEN`, `IG_USER_ID`, `IMGBB_API_KEY` | Facebook / Instagram publishing |
| `RESEND_API_KEY` | e-mails about new inquiries (resend.com) |
| `VIBER_CHANNEL_TOKEN` | Viber channel publishing |

The backend logs in to Vault with **AppRole** (read-only on that path). Locally the role id and secret id come
from `../premium-cars-infra/vault/secrets/backend-approle.properties`, written by `docker compose up` in
premium-cars-infra; in production set `SPRING_CLOUD_VAULT_APP_ROLE_ROLE_ID` / `..._SECRET_ID` and `VAULT_ADDR`.
If Vault is down, sealed or refuses the login, the backend does not start (`fail-fast`).

Change a value: Vault UI at http://127.0.0.1:8200 (root token in `premium-cars-infra/vault/secrets/init.txt`) →
`secret` → `premium-cars/backend` → *Create new version*, then restart the backend. Moving an old `.env`
into Vault: see premium-cars-infra's README.

## Admin login

The admin panel uses a server session: `POST /api/admin/login` sets the HttpOnly cookie `PC_SESSION`
(SameSite=Strict, Secure with `APP_SECURE_COOKIES=true` in production, 8 h); the browser never stores the
password. Changing requests need the CSRF token: the frontend reads the `XSRF-TOKEN` cookie and sends it as
`X-XSRF-TOKEN` (`GET /api/admin/csrf` sets it). Users are in `admin_user` (bcrypt hashes).

- First start: when `admin_user` is empty, user `admin` is created with `ADMIN_INITIAL_PASSWORD` from Vault
  (premium-cars-infra writes it to `vault/secrets/admin-initial-password.txt`). Change it in the admin panel
  (Профил); the value in Vault is not used again.
- 5 wrong passwords lock the user for 15 minutes; an unknown user gets the same answer as a wrong password.
- Rate limits per client IP: login 10 / 5 min, public inquiry form 5 / 10 min (HTTP 429).
- More admins ("Потребители" in the admin panel, `/api/admin/users`): every admin has the same rights and can
  create, reset and delete the others (not themselves, not the last one). A new or reset user gets a one-time
  password (shown once to the admin who made it) and must choose an own one at the first login; until then only
  `/me`, `/password` and `/logout` work (HTTP 403 otherwise).
- Sessions end when the user is deleted or the password changes (a reset, or a change in another browser):
  `AdminSessionFilter` compares the session with `admin_user` on every admin request.
- Forgotten password: another admin resets it. If nobody can log in: `DELETE FROM admin_user;` in the database,
  then restart: user `admin` is created again from `ADMIN_INITIAL_PASSWORD` (change it in Vault first).

## Importing cars

In the admin panel paste a listing URL; the backend downloads the page and photos and creates a draft.
The listing's URL and id are kept with the car (admin only): the admin list shows them with a link to the
original, its search box finds a car by the pasted link or listing id, and importing the same link again opens
the existing car.
Optionally enter the price and currency yourself (useful when the site hides the price).

| Site | How |
|---|---|
| global.autohome.com.cn (China) | page HTML first; if photos or EV data (battery, range, motor) are missing, the page is rendered in headless Chromium and the "More", "Electric Motor" and "Battery && Charging" tabs are opened |
| autowini.com (South Korea) | logs in with your autowini account (Keycloak), then reads the listing; specs and photos also work without login, the price only with it |
| anything else | generic extractor: JSON-LD → `__NEXT_DATA__` → Open Graph → page text |

The autowini login comes from Vault (`AUTOWINI_USER`, `AUTOWINI_PASS`).

### Headless browser (Playwright)

The first import that needs rendering downloads Chromium (~150 MB) into the Playwright cache; later imports
reuse it. To turn rendering off (pages are then read from HTML only): `APP_IMPORTER_BROWSER_ENABLED=false`.

## Facebook and Instagram

The car editor in the admin panel shows the post text (the posting script's format, editable) with
**Publish to Facebook** / **Publish to Instagram** buttons, the list of earlier posts, and "share with photos"
(the phone's or Windows share sheet, e.g. to the Instagram app) / "download photos".

Publishing uses the Meta Graph API like the posting script: Facebook gets an album post with up to 10 photos;
Instagram gets a carousel (photos are uploaded to imgbb first, because Instagram needs public photo URLs).
Settings, in Vault like the other secrets (the same names as the script's `.env`):

| Key | What | Where to get it |
|---|---|---|
| `FB_PAGE_ID` | the Facebook page id | Page → About / Meta Business Suite → Settings |
| `FB_ACCESS_TOKEN` | a long-lived **Page** access token with `pages_manage_posts`, `pages_read_engagement`, `instagram_basic`, `instagram_content_publish` | developers.facebook.com → your app → Graph API Explorer → select the page → generate token; exchange it for a long-lived one (Access Token Debugger → "Extend") and take the page token from `/me/accounts` |
| `IG_USER_ID` | the Instagram **business/creator** account linked to the page | Graph API Explorer: `/{FB_PAGE_ID}?fields=instagram_business_account` |
| `IMGBB_API_KEY` | imgbb API key | api.imgbb.com |

A network whose settings are missing has its button disabled. Restart the backend after changing them in Vault.
Posts are recorded in `social_post` (link, date, number of photos); the editor asks before posting a car twice.

## Post templates and publishing

The texts for Facebook, Instagram and Viber come from templates, one per network, edited in the admin panel
("Шаблони") and stored in `post_template` (no row = the admin panel's default). Placeholders such as
`{{price}}`, `{{year}}`, `{{mileage}}`, `{{battery}}` are filled in by the admin panel from the car; a line whose
placeholder is empty for the car (e.g. the battery of a diesel) is left out. The phone, the Viber channel link and
the office (`{{phone}}`, `{{viber_link}}`, `{{office}}`) are shared by all cars: `post_setting`, edited on the
same page (`GET/PUT /api/admin/post-settings`; empty = the admin panel's default). The public site shows the
same details in its footer (`GET /api/public/contact`).

Publishing always goes through a confirmation step in the admin panel: the filled-in text (editable) and the car's
photos to pick from (1 to 10, sent in gallery order). `POST /api/admin/cars/{id}/social-posts` takes
`{network, text, imageIds}`; the ids must be photos of that car.

### Scheduled posts

The same dialog can schedule the post instead (1 minute to 90 days ahead): `POST /api/admin/cars/{id}/scheduled-posts`
with `{network, text, imageIds, publishAt}` (ISO instant). The text and photos are checked right away, like for
publishing now, and fixed. `ScheduledPostService` checks every 30 seconds and publishes the due posts for all three
networks (Instagram's API cannot schedule, so Facebook's own scheduling is not used either: one mechanism, visible
and cancellable in the admin panel). `GET /api/admin/scheduled-posts` lists the waiting ones and those of the last 7
days ("Насрочени"); `DELETE /api/admin/scheduled-posts/{id}` cancels a waiting one.

- A failed post is **not** retried: a network can fail half-way (Viber photos out, the text not), and a retry would
  post twice. It becomes FAILED with the reason; publish it again by hand.
- A restart while a post is being published leaves it FAILED ("interrupted") for the same reason.
- Sold or archived cars are not posted (FAILED with the reason).

## Viber channel

The car editor's **Publish to Viber** posts the car to the Viber channel through the Viber Channels Post API:
each photo is its own message (the photos picked when publishing), then the post text. Photos go
through imgbb like for Instagram (Viber loads them from public URLs) and are scaled down to 1 MB when bigger.
Posts are recorded in `social_post` (network `VIBER`, no link: channel messages have none).

| Key (Vault) | Where to get it |
|---|---|
| `VIBER_CHANNEL_TOKEN` | Viber app → the channel (you must be its superadmin) → channel info → **Developer tools** → Authentication token |
| `IMGBB_API_KEY` | the same key as for Instagram |

Viber accepts channel posts only after a callback URL ("webhook") is registered for the channel, and it checks
that URL right away, so the site must be reachable from the internet over HTTPS:

- **Production:** in the car editor, "Connect Viber channel" with the site's address (once).
- **Locally:** open a temporary tunnel to the frontend, e.g. `cloudflared tunnel --url http://localhost:3000`
  (prints `https://<random>.trycloudflare.com`), and connect with that address. Viber keeps the registration
  when the tunnel is closed; connect again only if posting answers `webhookNotSet`.

The callback is `POST /api/public/viber/webhook`; it accepts only requests signed with the channel token
(`X-Viber-Content-Signature`, HMAC-SHA256 of the body) and does nothing else. Posts are sent in the name of the
channel's superadmin (`get_account_info`). The token travels in the `X-Viber-Auth-Token` header.

## Inquiry e-mails

Every new inquiry is e-mailed to `APP_NOTIFY_TO` through Resend (resend.com): name, phone, e-mail (as reply-to),
the car with its link, the message and a link to the admin panel. The form must send `privacyAccepted: true`
(the customer ticked the privacy policy checkbox), otherwise HTTP 400. The mail goes out after the inquiry is saved
and on another thread (`InquiryNotifier`), so a failing mail service never loses an inquiry; failures are logged.
Off while `RESEND_API_KEY` (Vault) or `APP_NOTIFY_TO` is empty, e.g. locally. The sender address
(`APP_NOTIFY_FROM`, default `noreply@premiumcarsimport.bg`) must be on a domain verified in Resend.

## Docker image (production)

`Dockerfile` builds the production image: Java 21 on Ubuntu 24.04 with headless Chromium for the importer (installed
with the pom's Playwright version), running as a non-root user, photos under `/app/data` (a volume), health check on
`/actuator/health`. CI builds it on every pull request and pushes `ghcr.io/ilutov90/premium-cars-backend:latest` and
`:<commit>` on main. premium-cars-infra's `docker-compose.prod.yml` runs it; local development does not use it.

## Configuration

Everything else is in `src/main/resources/application.yml` (no secrets) and can be overridden with an
environment variable (or a git-ignored `.env` next to `pom.xml`, see `.env.example`):

| Setting | Variable | Default |
|---|---|---|
| Vault address | `VAULT_ADDR` | `http://127.0.0.1:8200` |
| Inquiry e-mails to | `APP_NOTIFY_TO` | empty (off) |
| Site address (links in e-mails) | `APP_SITE_URL` | `http://localhost:3000` |
| Vault on/off | `VAULT_ENABLED` | `true` |
| Database URL | `DB_URL` | `jdbc:postgresql://localhost:5433/premiumcars` |
| Secure cookies (HTTPS) | `APP_SECURE_COOKIES` | `false` (set `true` in production) |
| Swagger / API docs | `APP_API_DOCS` | `true` (set `false` in production) |
| Daily ECB exchange rates | `APP_ECB_RATES` | `true` (`false` = only the configured rates) |
| Fallback exchange rates | `app.pricing.exchange-rates` | approximate; used until the ECB answers and for currencies the ECB lacks |
| Max photos per import | `app.importer.max-images` | 30 |
| Headless browser | `APP_IMPORTER_BROWSER_ENABLED` | `true` |
| Demo cars on an empty DB | `LIQUIBASE_CONTEXTS` | `demo` (`none` = no demo data) |

Exchange rates: on start and every hour the backend reads the ECB daily reference rates
(`eurofxref-daily.xml`, published around 16:00 CET on working days). When a new day appears, all prices are
recalculated. If the ECB cannot be reached, the last rates (or the configured ones) stay in use. The admin panel
("Цени") shows the rates in use, their source and date (`GET /api/admin/pricing-profiles/exchange-rates`).

Prices are recalculated on every start; to recalculate by hand: `POST /api/admin/cars/recalculate-prices`
(from Swagger).

## Pricing

Customers see one final price that includes everything; the same number goes into the Facebook/Instagram post.
Each source site has its own formula in the `pricing_profile` table, edited in the admin panel ("Цени"):

```
final price = car price in € + base costs + step cost × steps above the threshold + profit
```

| | autohome (China) | autowini (South Korea) |
|---|---|---|
| base costs (all import costs up to the threshold) | 5860 € | 5000 € |
| step cost, for every 10 000 € above 10 000 € | 2880 € | 600 € |
| profit | 2000 € | 2000 € |

Above the threshold the step costs are proportional: autohome, car for 25 000 € = 5860 + 2880 (up to 20 000)
+ 1440 (the 5000 above 20 000) + 2000. The result is rounded to whole euros. Saving a profile reprices every car. Imported cars use their site's profile;
cars from other sites get one chosen in the editor.

Per car, the editor can correct the result (columns `profit_eur`, `fixed_total_eur`; empty = the formula):
**profit for this car** replaces the profile's profit in the formula, and **final price by hand** replaces the
whole result (the calculated price stays visible next to it). Repricing keeps both corrections.

## Data model

A car is `specs` (title, make/model/trim, year, mileage, fuel, transmission, drivetrain, engine, power,
battery kWh, electric range + cycle, motor kW, seats, doors, weight, dimensions, colour, notes, extra specs)
plus `pricing` (source price, currency, price profile). The public API returns only the final `priceEur`. The API uses the same nesting.

## Database access

No ORM. Each repository holds the SQL for its table:

| Class | Table | Note |
|---|---|---|
| `CarRepository` | `car` | search with a dynamic WHERE (`CarSearchSql`), sorting with `NULLS LAST` |
| `CarImageRepository` | `car_image` | position 0 = cover; positions are reordered with one SQL statement |
| `PricingProfileRepository` | `pricing_profile` | one row per source site |
| `SocialPostRepository` | `social_post` | posts published to Facebook / Instagram |
| `InquiryRepository` | `inquiry` | `LEFT JOIN car` for the car title |
| `AdminUserRepository` | `admin_user` | bcrypt hashes, failed attempts, lock, one-time password flag |
| `ScheduledPostRepository` | `scheduled_post` | posts planned for later; `claimDue` takes due ones with `FOR UPDATE SKIP LOCKED` |

Schema change: a new file `src/main/resources/db/changelog/changes/00N-....sql` and a line in `db.changelog-master.yaml`.
Never edit a changeset that has already run.

## When an import misreads a field

1. In the browser: "Save page as… → HTML only" for the listing.
2. Put the file in `src/test/resources/pages/` and add a test (`GenericPageExtractorTest`, `AutohomePageParserTest`
   or `AutowiniPageParserTest`).
3. Fix the parser (`importing/extract/`, `importing/source/autohome/`, `importing/source/autowini/`).

## Troubleshooting

| Symptom | Fix |
|---|---|
| `Connection refused` to 5433 | Is Docker Desktop running? `docker compose ps` in premium-cars-infra |
| Start fails: `Cannot create authentication mechanism` / `Status 400 ... invalid role or secret ID` | Vault is not set up or `backend-approle.properties` is missing: `docker compose up -d` in premium-cars-infra |
| Start fails: `Vault is sealed` / connection refused to 8200 | After a reboot: `docker compose up -d` in premium-cars-infra (unseals Vault) |
| Start fails: `password authentication failed for user` | `DB_PASSWORD` in Vault differs from the database: see premium-cars-infra README "Change the database password" |
| Admin login: "Сесията е изтекла" | The CSRF cookie expired with the session: reload the page |
| Port 8080 is taken | `SERVER_PORT=8081 mvn spring-boot:run` (and `API_URL=http://localhost:8081` for the frontend) |
| Liquibase checksum error | A changeset was edited after it ran; revert it and add a new file |
| `JdbcRepositoriesTest` is skipped | Docker is not reachable. Start Docker Desktop |
| autowini import: "login failed" | Check `AUTOWINI_USER` / `AUTOWINI_PASS` in Vault, restart the backend |
| autohome import lacks photos/EV data | Rendering is off or Chromium could not start; see the warnings on the import result |
